# Handoff: состояние проекта и история изменений

Этот файл — инструкция для следующего агента. Описывает текущее состояние
бота, архитектуру, деплой и что **нельзя ломать**.

---

## Текущее состояние (на 29.06.2026)

### Два независимых режима

| Режим | Назначение | Точка входа | Cron на сервере |
|-------|------------|-------------|-----------------|
| **Канал** | Пост в @prdsvac (продуктовый дизайнер) | `python -m bot.run_once fetch` | `0 10 * * *` |
| **Подписчики** | Личные дайджесты по роли | `python -m bot.run_once subscribers` | `2 10 * * *` |
| **Чат UI** | `/start`, выбор ролей, `/stop` | `python -m bot.chat_main` | watchdog `*/5 * * * *` |

**КРИТИЧНО:** логику канала (`service.py`, `run_once fetch`, парсеры канала)
**не менять** без явного запроса. Подписчики — отдельный слой (`subscriber_*`,
`chat_main.py`, таблицы `subscribers` / `subscriber_sent`).

### Подписчики (MVP)

0. **Флоу выбора ролей не хранит состояние.** Категория лежит в `callback_data`
   (`s2:role:<category>:<role>`, `s2:save:<category>`), отмеченные роли читаются
   из галочек клавиатуры (`_draft_from_keyboard`). FSM и MemoryStorage убраны:
   раньше рестарт `chat_main` обнулял их, и все открытые клавиатуры отваливались
   с «Сначала выбери специальность». Не возвращай FSM — состояние в памяти на
   shared hosting теряется постоянно.
1. Пользователь: `/start` → inline-кнопка роли → `subscribers` table
2. Cron `subscribers`: **сбор один раз на роль за прогон** (`_collect_roles_once`),
   дальше подписчики обслуживаются из кэша (`_merge_for_roles`).
   `collect_for_role` не зависит от пользователя — персонализация начинается
   позже, в `_filter_new_for_user` / `subscriber_sent`. **Не возвращай
   `collect_for_role` внутрь цикла по подписчикам:** один проход по роли — это
   165–390 запросов к источникам, и раньше они умножались на число подписчиков.
   Стережёт `tests/test_subscriber_service.py`
   **HH 403 не должен быть молчаливым.** Если HH ограничил запросы, роль
   собирается частично: `collect_for_role` бросает `SourceLimited` с тем, что
   успело собраться, подписчики получают это, а админ — строку «⚠️ HH ограничил
   запросы» (`DigestStats.limited_roles`). Подписочный сбор после 403 перестаёт
   ходить к работодателям бигтеха; канал — по-прежнему проходит всех
   (`stop_on_forbidden` только у `fetch_bigtech`). Стережёт `tests/test_hh_forbidden.py`
3. Per-user dedup через `subscriber_sent` (отдельно от канала!)
4. Если новых вакансий 0 — уходит «Новых вакансий … нет» (`format_empty_notice`),
   **не чаще раза в день** (`subscribers.last_empty_notice_on`) и **только если
   все роли подписчика собраны целиком** (`_roles_complete`): при сбое, 403 или
   неизвестной роли молчим — вакансии могли быть, мы их просто не увидели.
   До 24.10.2026 здесь была тишина; пользователь попросил писать, что вакансий нет.
5. **GeekJob и GetMatch — общие ленты, одна на прогон** (`shared_feeds` в
   `subscriber_collect.py`): обе площадки маленькие, весь каталог — несколько
   страниц. GeekJob: `search` игнорирует, `qs` сортирует по релевантности и
   отдаёт часть каталога со старыми вакансиями сверху — поэтому качаем все 3
   страницы. GetMatch: `specialization` игнорирует, отдаёт все IT-вакансии —
   поэтому лента идёт всем ролям, а не только дизайну (до 24.10.2026 был флаг
   `uses_getmatch`). Сбой любой из двух площадок роль не валит (`_side_source`),
   таймаут 20 с. Сайт Сбера (`BigTechCareersParser`) подписки не опрашивают:
   он подгружает вакансии скриптом и всегда находил 0; канал его пока вызывает.
   Стережёт `tests/test_side_sources.py`
   **Хабр Карьера** (с 24.10.2026) — такая же общая лента: вся выдача за 72 ч
   (`sort=date`, по 50 — больше сайт не отдаёт, ~14 страниц), даёт ~+10% к HH
   (больше всего Go, QA, Java, data). Внешний отклик на Хабре ведёт на сайт
   работодателя, а не на HH, — точного совпадения с HH по id нет.
   **Дубли между площадками** (`cross_source.py`): `dedupe_key` сравнивает почти
   дословно, а площадки пишут компанию по-разному. `merge_key` = название без
   пробелов и знаков + компания без кавычек, скобок, ОПФ и с короткой таблицей
   псевдонимов (Сбер/Сбер Банк, RWB/Wildberries, 2GIS/2ГИС, Банк ВТБ (ПАО)…).
   Грейд **не** выкидываем: «Младший»/«Старший» тестировщик одной компании —
   разные вакансии. Ключ хранится в `subscriber_sent.merge_key` — дубль с другой
   площадки не придёт и на следующий день. Замер 24.10.2026: точные дубли
   Хабр↔HH — 6 из 159, пропущенных обычным дедупом — ~3; после `merge_key`
   остаются 1–2 спорных на ~1700 вакансий. Стережёт `tests/test_habr_and_dups.py`
8. **Регион поиска** (с 24.10.2026): первый шаг /start — «СНГ», «Удалёнка по
   миру» или оба (`s0:reg:<cis|world|both>`, таблица `user_region`, по умолчанию
   СНГ). Мировые ленты (`parsers/world_remote.py`: Himalayas `worldwide=true`,
   We Work Remotely «Anywhere in the World», Jobicy `geo=anywhere`) — такие же
   общие ленты на прогон, собираются для всех; `regions.for_region` при раздаче
   оставляет человеку площадки его региона. Из мировых выкидываются названия с
   регионом («LatAm Only», «(US)» — площадка всё равно пометила «весь мир») и
   подработки по разметке ИИ («Research Expert (Python)»). Листание лент
   останавливается, когда на странице **не осталось** свежих: на первой
   странице Himalayas бывают закреплённые старые вакансии. Объём скромный:
   ~25–30 вакансий за 72 ч на все роли. Indeed/LinkedIn — нет API, блок ботов
   (403/429); Remote OK бесплатно отдаёт ленту с задержкой — пусто по нашим
   ролям; Arbeitnow — офисная Европа, пользователь выбрал только удалёнку.
   `QA_AUTOMATION_TERMS`: «automation» — только рядом с QA/test или как
   «Automation Engineer» в начале названия: без профобласти HH (Хабр, мир)
   попадали «Marketing/Messaging/Workflow Automation». Стережёт `tests/test_regions.py`
6. **Не больше 30 вакансий в дайджесте** (`MAX_VACANCIES_PER_DIGEST`): у нового
   подписчика «новые» — все вакансии за 72 ч, у продакт-менеджера это ~240, то
   есть ~20 сообщений подряд. Уходят самые свежие, отмечаются только они; остальные
   приходят в следующие дни, пока не устареют. В заголовке — «Показаны 30 самых
   свежих из N»; обещания «пришлю завтра» нет — часть успеет устареть.
7. **Кнопка «Показать остальные N»** под последним сообщением урезанной подборки
   (`bot/digest_more.py`). Рассылка кладёт остаток в `digest_overflow` (на
   человека — только последняя подборка, `digest_day` — её дата), чат-бот по
   нажатию (`cb_digest_more`, callback `dg:more:<YYYY-MM-DD>`) отдаёт его и
   отмечает в `subscriber_sent`. Остаток берётся по id нажавшего, из callback —
   только дата. Двойное нажатие не дублирует (замок на человека — чат-бот один);
   кнопка от старой подборки отвечает «Больше вакансий из этой подборки нет».
   Отметка ставится после отправки: при обрыве сети кнопка остаётся рабочей.
   Стережёт `tests/test_digest_more.py`

### Роли

Выбор двухшаговый: специальность (`role_categories.py`) → вакансии внутри неё
(`roles.py`), можно отметить несколько.

| Специальность | id ролей | professional_role HH |
|---------------|----------|----------------------|
| Дизайн | `product_designer`, `communication_designer`, `graphic_designer`, `art_director` | только `art_director`: 12, 34 |
| Frontend | `frontend_react`, `frontend_vue`, `frontend_angular` | — |
| Backend | `backend_python`, `backend_java`, `backend_go`, `backend_php` | — |
| Fullstack | `fullstack` | — |
| Mobile | `mobile_flutter`, `mobile_ios`, `mobile_android`, `mobile_react_native` | — |
| Продукт | `product_manager`, `product_owner` | 73 |
| QA | `qa_manual`, `qa_automation` | 124 |
| Data | `data_scientist`, `ml_engineer`, `data_engineer`, `data_analyst`, `product_analyst`, `data_governance` | — |
| Руководители | `head_of_data`, `head_of_ai`, `head_of_design`, `head_of_product`, `head_of_engineering` | — |

`fullstack` и `mobile_*` (24.10.2026, по просьбе подписчика — Flutter): общий
`NOT_DEVELOPER_EXCLUDE` отсекает «Fullstack-аналитика», «Fullstack QA», «Дизайнера
Fullstack» — это треть заголовков со словом fullstack на HH. Запросы «фуллстек» и
«dart» HH ищет нечётко (приносят Python и 1С) — не добавлять. Swift — только рядом
с разработкой («сопровождение SWIFT» — банк), Kotlin в Android — только с
mobile/Jetpack/Compose (иначе это бэкенд). React-роль не берёт React Native.
Мобильных вакансий мало: за 72 ч по всем площадкам iOS ~7, Android ~8, Flutter ~3,
React Native ~2. «Мобильный разработчик» без стека в названии не уходит никому.

`hh_professional_roles` нужен там, где по названию не видно отрасли. Для QA
(`124`) это работает отлично — уходит контроль качества на стройке и на
производстве. Для продакта (`73`) эффект частичный, поэтому дополнительно
работает `NON_IT_DOMAIN_EXCLUDE` в `role_filters.py`.

`product_manager`: «менеджер по продукту» по-русски — ещё и ведение товарной
линейки в фарме, FMCG, одежде, дистрибуции техники (в ночной выдаче HH — около
четверти из 248). `PRODUCT_MANAGER_GOODS_EXCLUDE` отсекает их по словам отрасли,
**но только если в названии нет цифрового признака** (сайт, приложение, e-com,
платформа, IT, AI…): «Product manager, fashion — развитие сайта» остаётся.
Ловушки, закреплённые тестами: «ко**мерч**еский» ⊃ «мерч», «**реле**вантность»
⊃ «реле», «внутренние инструменты» ≠ «строительный инструмент». Серую зону —
просто «Менеджер по продукту» у производителя труб — по названию не поймать.

`art_director`: «арт-директор» в РФ — ещё и ведущий программы в баре,
клубе, на концерте. Профобласть 12 («Арт-директор, креативный директор»)
одна режет и нужное — «Арт-директор/Дизайнер по упаковке» лежит в 34
(«Дизайнер, художник»), поэтому заданы обе, а заведения и мероприятия
добиваются `ART_DIRECTOR_EXCLUDE`. Креативный и дизайн-директор в роль
намеренно не входят — это соседние, но другие должности.

**Data.** Профобласти не заданы: ML-инженеров работодатели раскладывают
минимум по пяти областям, а названия у data-профессий однозначные.
Главные правила в `role_filters.py`:

- **ML и LLM — только как должность.** «Senior .NET Developer (LLM / RAG)»,
  «Golang-разработчик (домен AI&ML)», «Python-разработчик (ML)» — это
  разработчики, они остаются в своих ролях. ML-роль — когда ML/AI/LLM —
  сама должность: ML Engineer, ML-инженер, AI Engineer, MLOps, LLM-инженер,
  Computer Vision, инженер по машинному обучению.
- **BI — только как должность** (BI-аналитик, BI-разработчик, «Разработчик
  Power BI»): «JS-разработчик на BI-платформу» — фронтенд.
- **Backend отдаёт ровно то, что забирают ML/Data Engineer**
  (`_belongs_to_data_role`), не больше — иначе вакансия теряется между
  ролями. На живой выдаче это 4 AI-инженера из 66 у Python, у Java и Go — ничего.
- Системные аналитики (в том числе DWH) не входят ни в одну data-роль —
  это отдельная профессия.
- Совмещённые «DWH + BI» («ETL/BI разработчик») попадают и в Data Engineer,
  и в аналитики — это осознанно. Так же вакансии про качество данных попадают
  и аналитикам, и в Data Governance.

**Руководители.** Уровень директоров и руководителей направлений. Эти роли
*добавляют* вакансии, а не забирают их у профильных: Head of QA остаётся в QA,
Head of Data Science — у Data Scientist. Правила в `role_filters.py`:

- **Тимлидов не берём** (`LEADER_EXCLUDE`: «Руководитель группы/команды», Team
  Lead) — их ловят профильные роли, а руководитель, подписанный на категорию,
  не должен получать вакансии своей команды.
- **«Технический директор» — только с IT-признаком** в названии (CTO,
  разработка, IT, геймдев, финтех…). Профобласть HH 125 «Технический директор
  (CTO)» стройку и заводы не отсекает — проверено на выдаче.
- **Поиск HH по «директору по разработке» отдаёт девелопмент и Business
  Development** — отсекается в `HEAD_OF_ENGINEERING_EXCLUDE`.
- **Голое «Руководитель отдела аналитики»** засчитывается в Head of Data только
  с признаком данных рядом (Python, SQL, BI, метрики, «данных»): иначе это
  аналитика доходности, аудита, животноводства.
- **Остаточный шум:** «Технический директор (CTO)» у нетехнологических компаний
  (стекольный завод, охрана) — по названию не отличить, компания в матчер не
  передаётся. Вакансий руководителей мало — около одной в день на все роли,
  дайджест приходит не каждый день.

`frontend` и `backend` без суффикса — **legacy**: остались в `ROLES` ради уже
подписанных пользователей, но в меню не показываются (нет в `role_categories.py`).

Расширение на fullstack, QA, PM и т.д. — добавить в `roles.py` + `role_filters.py`
+ в нужную категорию в `role_categories.py`.

## Команды для пользователей (chat_main)

**Основной UI — кнопки меню внизу чата:**

| Кнопка | Действие |
|--------|----------|
| Выбрать роли / Выбрать роли заново | Шаг 1 (специальность) → шаг 2 (мультивыбор вакансий) |
| Мои вакансии | Текущая подписка |
| Прекратить рассылку | Отмена рассылки |

Команды `/start`, `/myrole`, `/stop` оставлены как fallback.
`/stats` и `/users` — админка, только для `TELEGRAM_ADMIN_ID` (без него
команды не отвечают никому). Подробности — в разделе «Админка и метрики».

### Разовые рассылки (ченжлоги)

Текст — файл `broadcasts/<id>.html` (HTML Телеграма), id рассылки — имя файла.
`run_once broadcast --file …` без флагов шлёт **только превью админу**; всем —
только с `--send`. `--include-starters` — ещё и тем, кто нажимал /start, но не
подписался (бот знает их только с выкатки админки). Отписавшимся не шлём.
Доставка отмечается в `broadcast_sent` после ответа Телеграма, поэтому
оборванную рассылку (сеть на reg.ru рвётся) можно просто перезапустить —
дубликатов не будет. Для новой рассылки — новый файл, а не правка старого.

### Админка и метрики

- **Активный** — что-то сделал в боте (сообщение или нажатие кнопки).
  `TrackActivityMiddleware` в `chat_main.py` пишет одну строку на человека в
  день в `user_activity` (день — по `TIMEZONE`). Отсюда DAU и MAU (30 дней,
  включая сегодня). Служебные апдейты вроде `my_chat_member` не считаются.
- **Охват** — получил хотя бы один дайджест (`subscriber_sent`). Для бота-
  рассылки это главная цифра: подписчик может месяцами читать и ничего не
  нажимать, а прочтения Телеграм боту не сообщает. **Не засчитывай получение
  дайджеста как активность** — иначе DAU станет копией охвата.
- **Отток** — `subscribers.unsubscribed_at` и `unsubscribe_reason`
  (`stop` — отписался сам, `blocked` — заблокировал бота, ловится на
  `TelegramForbiddenError` при рассылке). Повторная подписка их обнуляет.
- **Имена** в `/users`: из апдейтов (активные), из ответа Телеграма на
  отправку дайджеста (молчаливые подписчики) и через `getChat` при открытии
  страницы — для всех, кого бот знает только по id, включая отписавшихся
  (`_fill_missing_profiles`, только текущая страница, найденное сохраняется).
- **Ссылки** `tg://user?id=` Телеграм молча убирает, если у человека закрыта
  пересылка сообщений, — бот это не обойдёт. Поэтому в строке есть @username
  (кликабелен всегда) и id в `<code>`: копируется по тапу, а без него клиент
  подсвечивает десятизначные id как телефон.
- Тексты сообщений **не храним** — только факт действия и профиль.
- Админ исключается из **всех** чисел `/stats`, не только из «Аудитории».
- Блоки «Подписчики» и «Рассылка» считают только **нынешних** подписчиков:
  строки `subscriber_roles` и `subscriber_sent` у отписавшихся не удаляются, и
  раньше из-за них роли завышались, а «получили хотя бы 1 вакансию» доходило
  до 133%. По ролям считаются люди («подписаны · получали вакансии»), а не
  вакансии: по какой роли ушла вакансия, бот не хранит. Стережёт
  `tests/test_admin_counts.py`.
- Учёт активности начался с выкатки админки — DAU/MAU раньше этой даты
  не восстановить; `/stats` пишет, с какого дня идёт счёт.

Пользователь **обязан** написать `/start` первым — иначе Telegram не даст
слать сообщения в личку.

## Исправленные баги (история)

### Канал

1. **Вечная блокировка вакансий без даты** — сохранять только опубликованные
2. **GetMatch date parse** — `parse_iso_datetime` вместо `fromisoformat`
3. **URL не экранирован** — `escape_html` в href
4. **GitHub cron задержки** — переезд на ISPmanager
5. **TelegramNetworkError** — retry в `_safe_send`
6. **Python 3.8** — `backports.zoneinfo`
7. **remote-job.ru удалён** — дублировал HH

### Подписчики (29.06.2026)

1. **watchdog + pgrep** — на reg.ru `pgrep` не находил процесс; заменено на `ps aux | grep chat_main`
2. **Двойной chat_main** — pid-file lock в `chat_main.py`
3. **Смена роли** — раньше очищала `subscriber_sent`; с 24.10.2026 история
   сохраняется: стирание приводило к повторной отправке уже присланного, а
   вакансии новых ролей и так новые (другие uid)
4. **Пустая рассылка** — была тишина, с 24.10.2026 — «новых нет» раз в день (см. выше)
5. **Flood** — пауза 50 ms между подписчиками

### Чат-бот (09.08.2026)

1. **Watchdog не мог поднять бота** — `watchdog.sh` писал `echo $! > chat-bot.pid`
   раньше, чем питон стартовал. `_acquire_single_instance` читал файл, видел
   **собственный** pid, `os.kill(pid, 0)` проходил → «уже запущен» → `sys.exit(1)`.
   Ручной запуск работал, запуск через watchdog — всегда самоубийство: бот лежал,
   а в лог каждые 5 минут капало «Чат-бот уже запущен».
   Починено в двух местах: watchdog больше не трогает pid-файл (владелец — сам бот),
   и свой pid в файле больше не считается конфликтом. Тесты — `tests/test_single_instance.py`.
2. **Клавиатуры умирали при рестарте** — FSM жил в `MemoryStorage`, после
   перезапуска нажатие роли давало «Сначала выбери специальность». Убрано
   состояние целиком (см. «Подписчики», п. 0). Тесты — `tests/test_chat_flow.py`,
   в частности `test_keyboard_still_works_after_restart`.
3. **QA и PM тонули в не-IT** — «тестировщик техники», «инженер по качеству
   (дорожное строительство)», «Продакт-менеджер товарного направления»,
   «Product Manager (медицинские изделия, стоматология)». Добавлены
   `hh_professional_roles` и `NON_IT_DOMAIN_EXCLUDE`; этот мусор с живой выдачи
   HH ушёл, пересечений между ролями не осталось.
4. **Рассылка пересобирала всё заново на каждого подписчика** — стоимость была
   (подписчики × их роли) вместо (различных ролей). Десять подписчиков на
   `product_designer` = ~3900 запросов и ~13 минут ради десяти одинаковых
   ответов. Опаснее медленности был тихий отказ: при 403 `_search` обрывает
   обход целиком, роль собирается пустой, а пустая роль внешне неотличима от
   «сегодня новых нет» (DM не отправляется). Теперь сбор кэшируется по роли,
   а несобравшиеся роли уходят админу отдельной строкой в `run_once subscribers`.
5. **Пропуски в паттернах QA и PM** — живая выдача показала незакрытые формы:
   «Автотестировщик», «Тестировщик-автоматизатор», «QA Lead (Manual +
   Automation)», «Менеджер по продукту», «Проектный менеджер». Все добавлены
   в `role_filters.py` и закреплены тестами в `tests/test_role_filters.py`.

## Известные ограничения

- **Канал и подписчики** используют одну SQLite БД, но разные таблицы дедупа.
  WAL включён (`PRAGMA journal_mode=WAL`).
- **HH даты** приходят в формате `+0300`; `parse_iso_datetime` нормализует его в `+03:00`.
- **Дубли между площадками**: `merge_key` ловит разное написание компании и
  пробелы, но не разные названия одной вакансии («ML-инженер» и «ML-инженер
  senior», «… (Java)» и «… (Java) / Performance Engineer»). Такие единичны.
- **Тесты не ходят в сеть** (`tests/conftest.py` блокирует aiohttp): новую
  площадку в тестах сбора нужно подменять, иначе она молча вернёт пусто.
- **Фильтры frontend/backend** — эвристика по title, возможны false positive/negative.
- **`project_manager` сознательно не добавлен.** Роль была написана и проверена
  на живой выдаче HH — и выброшена: «Руководитель проектов» в РФ доминируют
  стройка, производство и энергетика, а HH держит их под тем же
  `professional_role=107`, что и IT. Даже со словарём предметных областей
  сквозь фильтр проходило ~⅓ мусора вроде «Руководитель проектов (энергетика)».
  Не добавляй её обратно, не решив, чем отделять IT — заголовок и профобласть
  HH для этого не годятся.
- **shared hosting** — `chat_main` может падать; watchdog перезапускает каждые 5 мин.
- **Повторный ручной `subscribers`** в тот же день безопасен: вакансии уже в
  `subscriber_sent`, а «новых нет» отмечено в `last_empty_notice_on`.

## Обновление на сервере — автодеплой (с 24.10.2026)

Push в `main` → `.github/workflows/tests.yml` (Python 3.8 в контейнере, как на
сервере; check run называется `tests`) → CRON на сервере каждые 5 минут
запускает `deploy/isp/autodeploy.sh`:

- не трогает бота 09:55–10:40 МСК и пока работает процесс python `bot.run_once`
  (отложенная рассылка `bash -c 'sleep …'` не в счёт — ищем процесс python);
- новый коммит в `origin/main` → смотрит check run `tests` через публичный API
  GitHub (без токена); идут — ждёт, упали — пишет админу один раз и коммит
  больше не пробует (`logs/autodeploy.failed`);
- `git merge --ff-only`, при изменении `requirements.txt` — `pip install`;
- смоук: импорт `bot.run_once`, `bot.chat_main` и миграция базы; не прошёл —
  `git reset --hard` на прошлый коммит и сообщение админу;
- перезапуск `chat_main`; итог — сообщение админу (`bot/admin_notify.py`).

Watchdog и автодеплой берут общий замок `logs/bot-control.lock` (flock), а бота
запускают с `9>&-`, иначе он унёс бы замок с собой. Без замка 24.10.2026 два
скрипта подняли по копии, вторая вышла с ошибкой. На старте бот ждёт связь с
Телеграмом сам (`_wait_for_telegram`, ~3 минуты): раньше обрыв сети в момент
getMe ронял его до следующего обхода watchdog.

Проверка скрипта без сервера: `bash scripts/test_autodeploy.sh` — «GitHub» как
локальный bare-репозиторий, ответы API через `file://`, четыре сценария.

Вручную, если автодеплой отключён:

```bash
cd /var/www/u3452280/data/vacancy-bot
git pull
.venv/bin/pip install -r requirements.txt   # если менялся requirements.txt
pkill -f bot.chat_main || true
rm -f logs/chat-bot.pid && nohup .venv/bin/python -m bot.chat_main >> logs/chat-bot.log 2>&1 &
```
